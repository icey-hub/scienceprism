## 1. 产品目标与完成标准

面向已有论文或准备写论文的个人研究者，默认体验为：

**打开项目 → 在文稿中选内容 / 描述任务 → 按需调用 Skill → 查看修改 → 接受 → 编译与定位错误。**

项目的价值是把文稿、引文、修改审阅和编译上下文放在一起。本计划以这条连续操作为主；研究阶段、实验和多 Agent 保留为专业任务入口。

完成标准不是“又增加了多少功能”或“测试数增长”：

1. 润色、编译排错、引用核对三个任务能在工作台中完成，不要求先完成研究阶段、切换执行引擎或理解角色名称。
2. 用户能看清 AI 读了哪些材料、用了哪个 Skill、现在进行到哪一步，以及结果是文字回答、待接受修改还是实际编译成功。
3. 保存、刷新、取消、失败、重复点击和接受修改有一致行为；运行期间人工修改的内容不会被旧提案覆盖。
4. 实际任务的步骤数、完成时间、人工返工、模型请求数和供应商用量有前后记录，失败样例也保留。

| 已看到的结构 | 用户可能遇到的影响 / 实施前要验证的场景 | 代码入口 |

## 3. 功能取舍

| 处置 | 范围 | 具体做法 |
| --- | --- | --- |
| 作为默认核心 | 文件与编辑、一个助手入口、修改审阅、PDF / 编译错误、引用材料 | 在同一工作台完成常用操作；主操作使用“提问、修改、接受、编译”等用户语言 |
| 合并 | Chat / Agent 对话，润色 / 翻译 / 排错等任务入口，重复的修改提案处理 | 一个对话历史、一种任务状态、一套提案应用；“只读问答 / 允许提出修改”作为有意义的能力选择 |
| 收到按需入口 | 八阶段研究流程、任务审计、角色 / 约束详情、运行引擎设置 | 数据与旧链接继续可达；首次打开项目优先进入工作台，高级详情从对应任务展开 |
| 继续保留但不扩展 | 多 Agent 写作、实验运行、绘图、OCR、协作 | 先维护已有调用和数据兼容；不纳入首批核心体验验收，不用隐藏入口代替正确维护 |
| 在迁移验证后删除 | 后置打字动画、旧的重复 AI 提交路径、重复 patch 写回、失去调用者的组件 / 依赖 | 每项删除都有替代路径与调用检查；不按文件大小或依赖数量机械删除 |

普通提案的接受属于必要的改动确认，阶段审批属于研究流程；收缩导航时不把二者一并取消。

## 5. 关键实现决定

- **复用 Harness 的 Run、事件、决策与应用接口。** 普通编辑对话接入这一条链路；角色和能力由后端校验。自动补全保留适合短请求的独立入口，不强行迁移所有专用服务。
- **保留已有可执行约束。** 合并对话时仍支持现有三类约束提案及人工决定；只读问答不获得写入或命令执行权限。
- **先提供真实运行状态。** 复用运行查询与事件，停止必须到达模型和工具。真实文本增量传输只有在当前接口可以简单接入时才做；完整文本加真实状态可以先验收，删除收到全文后的假打字等待。
- **参与任务的文稿先保存，再记录版本。** 保存失败就不启动任务；协作文件先 flush。AI 读文件和产生修改时关联其基准版本，应用时同时检查服务端文件与编辑器未保存草稿。
- **修改只有一个应用入口。** 服务端预检所选文件、原始版本和约束；明确多文件失败与恢复语义。先支持按文件接受 / 拒绝，不再造完整 Git 或任意粒度合并系统。
- **Skill 与研究阶段绑定分离。** 可复用的名称、摘要、正文读取形成共同目录；现有 `stages` 绑定仍有效。兼容普通文本 Skill 不等于兼容外部脚本、MCP、网络权限或所有 Codex 工具，缺能力时显示原因。
- **按需上下文。** 默认提供选区、相关正文、明确加入的材料和必要日志；工具按需读更多内容。避免前端拼整份项目文本后后端再次打包。
- **随功能收口拆模块。** 助手、修改审阅和编译分别管理自己的状态与副作用，`EditorPage` 负责组装。先迁移一个模块并验证，再删除它的旧实现；不预建通用 Agent 框架。

借鉴依据沿用已核对的 [Aider / OpenCode / TeXlyre 研究](../docs/agent-governance/open-source-simplification.md)，分别参考局部修改、按需 Skill、编辑编译联动。本计划没有复制上游代码或引入候选项目依赖。

## 6. 验收方法

固定一个小型多文件 LaTeX 项目，含 `.tex`、`.bib`、一处可定位编译错误和可核对的引用；用户真实论文采用独立副本，原始文件保持可恢复。

| 场景 | 必须得到的结果 |
| --- | --- |
| 润色一段并追加“保留术语” | 只提出相关修改；追问保留上下文；接受后文本和 Run 记录一致 |
| 修复一条编译错误 | 指向真实文件 / 行；提出可审阅修复；接受后实际编译成功，PDF 对应本次源码 |
| 核对并补齐一条引用 | 来源、元数据与待确认项明确；BibTeX / cite 修改可审阅；未查到时保留未验证状态 |
| 运行中停止与重复点击 | 终态正确，后续工具 / 模型调用停止；重复点击不会创建重复工作 |
| 生成期间人工改文稿 | 旧提案报告冲突；用户的新内容不会被覆盖 |
| 刷新 / 失败 / 重试 | 历史和待审阅结果可恢复；失败不显示为成功；重试范围清楚 |
| 多文件应用中发生错误 | 应用范围与实际磁盘一致；回滚 / 恢复可验证，不出现不可解释的半完成 |

比较同一配置的改造前后：操作步骤、任务完成时间、人工修订次数、模型请求数、供应商 token。没有供应商用量就记缺失，不把估算冒充实际值。三个常见任务每类保留成功与失败样例；没有足够样本时不报告“成功率提升百分比”。

自动验证采用聚焦后端测试、类型检查与实际浏览器流程；每个实现切片收尾按仓库约定运行 `npm run quality`。模型调用遵守串行单发。用户审阅主界面与实际修改结果，构成产品验收的一部分。

## 7. 边界与风险

- 旧 AGENTS 的“非目标”包含不改视觉设计、不重构 EditorPage。本计划提出的是新的产品改造范围；用户已授权实施，AGENTS 已同步放开对应边界。
- 导航收缩先保留数据、旧路由和高级入口；确需移除持久化能力时另写迁移办法。
- 合并助手会影响约束提案、只读审查、模型配置与历史显示；T01–T02 要做兼容验证，不能只检查新按钮。
- 多文件应用和协作状态是高风险点，在主要界面改造前先处理版本冲突与失败恢复。
- 模型质量单独记录。如果在明确上下文和工具都正常时仍无法完成任务，再根据实际案例调整模型 / Skill；不把编排复杂度当作质量保证。
- 暂不纳入多 Agent 扩张、Skill 市场、云服务、移动端、替换整个技术栈或大规模视觉重绘。
