# 实施计划：研究流程中的真实子 Agent

## 现状与目标

当前的 8 个 Agent 角色只是单次 Harness Run 的权限和输出定义。研究流程的 `runResearchHarnessStage` 对每个阶段只启动一个 `research-stage-assistant` Run；阶段任务只记录一个 Run ID。产品没有委派子任务、父子 Run 关系或子 Agent 结果汇总。

目标是在**写作阶段**先完成一个可关闭的纵向试点：一个协调 Agent 把两项只读审查任务交给独立子 Agent，汇总审查结果后生成现有格式的写作 Brief，最终仍由研究者确认。完成标准是能在 SciencePrism 中看见真实的多个 Run、各自输入/输出/状态和父子关系，而非只在界面显示多个角色名。

## 设计决定

1. **先复用现有角色。** 协调 Agent 使用 `research-stage-assistant`；两个子 Agent 各使用独立的 `paper-reviewer` Run，分别审查论断与证据对应关系、方法与结论的一致性。它们有独立任务说明、上下文快照和结果。若试点证实两种审查需要不同权限或输出契约，再增设专门角色。
2. **先串行调用。** 子 Agent 1 → 子 Agent 2 → 协调 Agent，所有模型请求逐个等待完成，遵守 U-20 的本机共享网关约束。最多两名子 Agent，委派深度为 1；本轮不做递归或并行。
3. **显式的运行谱系。** 协调 Run 先创建但不启动；两个子 Run 以 `parentRunId` 和任务类型关联它，完成后才启动协调 Run。阶段任务保存三个 Run ID 及其状态，后端可按父 Run 查询子 Run。运行历史截断、进程重启和取消时仍须保留可解释的谱系与终态。
4. **权限和证据由代码把关。** 子 Run 的有效能力必须同时受项目策略、父 Run 和角色限制，试点只给 `project.read`。子 Agent 的审查文字不能直接变为已确认 Evidence 或论文事实；协调结果仍通过当前写作阶段 Schema 与 Evidence Ledger 校验，并保留人工审批。
5. **可选择试用。** 写作阶段增加“单 Agent / 多 Agent 审查”模式，默认保持现行路径。试点失败时显示具体子 Run 的错误并让用户重试，不把失败伪装成已完成的单 Agent 结果。

## 依赖顺序与验收点

详细任务及逐项验收见 [任务清单](todo.md)。实施顺序：运行谱系与权限 → 串行编排 → 写作阶段接入 → UI 可见性 → 端到端验证。每项完成后运行对应聚焦测试；每 2 项执行一次 `npm run quality`；最后用本项目的写作工作流真实走一遍多 Agent 模式，并检查审查记录、最终 Brief 和人工确认状态。

## 风险与处理

| 风险 | 处理 |
| --- | --- |
| 多次模型调用增加时延和费用 | 显式选择模式；限制为 2 个子 Run、固定顺序和总运行预算；界面显示实际用量。 |
| 运行中断导致悬空父子关系 | 父 Run 在子任务期间保持未启动状态；保存每步进度；重启后能识别并恢复或标记失败，不自动重复提交已完成的模型调用。 |
| 子 Agent 幻觉或引用未确认材料 | 子结果标注“审查意见”；协调输出继续走 Schema、Evidence Ledger 和人工审批。 |
| 历史 Run 列表只保留最近 100 条 | 设计时先确认关联 Run 的保留与查找策略；必须通过超过 100 条运行后的谱系回归测试。 |
| 本机网关并发冲突 | 编排器以 await 串行发起所有模型请求，测试中断言最大同时运行数为 1。 |

## 范围边界

试点仅接入写作阶段，不替换检索、创新点和方法阶段；不让子 Agent 自动执行实验、写项目文件、确认文献或批准阶段；不改变既有单 Agent 模式的输出契约。扩展到其他阶段需要先比较试点的审查收益、失败率、延迟与模型用量。
